# Filter inspection and analysis contract, version 1

Tracking: #403. The public entry point is `analyzeSnapshot(snapshot)` in `index.mjs`. `validateSnapshot(snapshot)` checks the boundary without running rules. Both are synchronous, independent of browser/native globals, and retain no mutable state. Inputs must contain only JSON-compatible data and must not be mutated. Results are newly allocated; consumers own their lifetime and reconciliation.

## Snapshot

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Exactly `1`; unsupported versions are rejected. Separate from backup format versions. |
| `snapshotId` | Nonempty acquisition identifier, generated by the producer, returned in successful analysis results. |
| `source` | `live` in version 1. Offline adapters and unknown runtime observations require a later contract extension. |
| `accountId`, `accountType` | Profile-local account key and server type. Neither is a cross-profile identity. |
| `count` | Native account filter count, not finding count. |
| `checks` | Nonempty selection of `runs`, `folders`, `addons`, `conditions`. Deduplicated in first-occurrence order. |
| `trial` | Existing trial feedback or `null`; consumer presents it. Analysis does not consume usage. |
| `allowed` | Optional; `false` indicates denied acquisition, with no successful analysis result. |
| `capabilities` | Native `runnableTypes` bitmask, explicit `supportsMixedConditions` boolean, `folderActionTypes` array, `customActionType` and `customTermAttribute`. Explicit enum values avoid hardcoding native constants in portable rules. |
| `entries` | Filter inspection entries, in native list order. Empty for denied acquisition. |

Each entry has `token`, zero-based `position`, `entity`, `observations`, and `errors`.

The token is an opaque live session reference, retained only for explicit edit requests. The native API verifies exact-object identity before edits. Position and name are display data, never write identities. Tokens and snapshots must not be written into backup files or used across profiles.

## Entity projection

The entity uses existing backup field names: `filterName`, `enabled`, `unparseable`, `filterType`, `actionList`, and `searchTerms`. It is an **inspection projection**, not a complete restorable filter. Never pass it to restore or persist it as a backup. This first step deliberately leaves the existing full backup serializer unchanged pending the fidelity audit.

- `filterType` is acquired for the `runs` check.
- Actions preserve native order and numeric `type`; relevant folder actions include `targetFolderUri`, and custom actions include `customId`.
- Terms preserve native order, `attrib`, `op` (including zero), `customId`, `matchAll`, `booleanAnd`, `beginsGrouping`, and `endsGrouping`.
- Inspection does not read search values, raw native text, descriptions or localized labels. It does not normalize grouping or deduplicate terms.
- Collections remain arrays even when unparseable or partially unreadable. Do not interpret their absence of data without examining `errors` and `unparseable`.

## Native observations and errors

`observations.canEdit` records native editability. `observations.actions` and `.terms` align with their entity arrays by zero-based position. Action observations may have `folder` or `provider`; term observations may have `provider`. Values are `available` or `missing`. An omitted property means that observation is not applicable or was not requested, not that it succeeded. Producers must supply all applicable facts for successfully acquired requested checks; version 1 accepts live snapshots only.

Missing folder/provider lookup follows the existing native lookup behavior, including native lookups that signal absence by throwing. Other errors reading action/term collections produce category-scoped `{category, code: "inspection-failed", details}` records. These suppress conclusions for the failed category on that filter and produce a visible inspection-failed finding. Other filters and categories remain analyzable. A failed account/list acquisition rejects the API call; it is not an empty successful account.

## Results

Successful results contain `snapshotId`, `analysisVersion`, `accountId`, `count`, deduplicated `checks`, `findings`, `diagnostics`, `complete` and `trial`.

Findings preserve the existing review model: `id`, `token`, `accountId`, `filterName`, `category`, `reason`, `enabled`, `canEdit`, `state`, and optional evidence (`position`, `targetFolderUri`, `customId`, `details`). IDs combine session token, category, reason and evidence position to preserve remedy-refresh reconciliation within a session. They are not persistent identities. `analysisVersion` identifies rule behavior independently of snapshot schema version.

`diagnostics` copies structured inspection errors with entry/account references. `complete` means no inspection errors were reported; it does not mean no problems or unparseable filters were found. Denied results contain only `{allowed: false, trial}` and must not be merged into successful review state.

Ordering is deterministic: input entry order, deduplicated check order, then action/term order. Analysis generates no timestamps or random IDs, performs no I/O, uses no hidden cache, and does not localize messages. Raw diagnostic details are not policy inputs.

## Consumers and extension points

The existing troubleshooter page calls `FiltersAPI.getFilterSnapshot()` and analyzes the response through this component. Its review state, localization, controls and rendering remain unchanged. Background workflows can import the same component with their own state; importing it does not share state between execution contexts.

New checks should acquire only necessary native evidence and implement portable policy here. A new check requires an explicitly supported check identifier, acquisition requirements, validation and rule tests. Backup/restore adapters will later reuse rules after full entity fidelity and unknown/offline facts are specified. Scheduling, storage and the future VFS adapter remain outside this component.
